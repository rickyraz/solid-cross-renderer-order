Pointer events and raycasting

@solidjs/universal knows nothing about events. A prop like onClick reaches the renderer as an ordinary prop, so the renderer stores it, and a small event system does what the browser does for DOM elements:

  • Hit testing. Each pointer event casts one ray from the camera through the pointer, against the whole scene, nearest hit first.
  • Bubbling. The event goes from the hit mesh up through its parents. Clicking A also counts a click on the slots group. B calls stopPropagation(), so its clicks stay on B.
  • Hover. Only the nearest hit and its parents are hovered, like :hover. A hovered box turns yellow, because the handler writes a signal that drives the material's color prop.
  • Pointer capture. Press on a box and drag sideways to spin it. The box calls setPointerCapture(), so it keeps getting moves even when the pointer leaves it. The spin mutates rotation directly, without a signal.
  • Click means down and up on the same object. A drag from A to B is a click on neither, but their shared slots group gets one, as a DOM click goes to the common ancestor.
  • Disposal. When a hovered or captured box is unmounted, it is dropped without a pointerout: its owner is gone, so its handlers must not run. The component clears its own hover state with onCleanup.

Try it: hover a box, click A then B and compare the group count, press on A and drag sideways past B, or unmount the boxes while one is hovered.

Async loaders and shared resources

This example has its own canvas and WebGLRenderer, so its GPU counters stand alone. Each box waits for a texture from a slow loader. The left and middle boxes ask for the same texture, so they share one. The right box has its own.

  • Loading. The texture is read through an async createMemo. Until it arrives, Solid's <Loading> shows a wireframe box. The boundary works through the three renderer like any other component.
  • Shared resources. A reference-counted cache in plain JavaScript, with no Solid and no three, loads each key once. Hide the left box and the texture stays for the middle one. Hide both and the texture is disposed.
  • The old texture stays on screen. Click Next shared texture. In Solid 2, content that has rendered keeps showing while the new texture loads. A texture must not be released until its replacement is on screen.
  • Two release strategies. The Solid binding can release in the async memo's onCleanup (naive), or in the cleanup of an effect, which runs only once the replacement is committed (committed). I expected naive to dispose the texture on screen. It does not: in Solid 2.0.3, the onCleanup of the run on screen waits until its replacement lands. A run that never reached the screen is cleaned up at once. I found this behavior only by testing, not in the docs, so committed is the strategy to rely on.
  • Late disposal. Hide a box while its texture is still loading. When the texture arrives, nobody wants it, so the cache disposes it at once.

Per-frame loop

Animation needs code that runs every frame, outside Solid's reactivity. The frame loop is plain JavaScript: each frame it runs its subscribers, calls a beforeRender hook, and draws. The Solid binding adds two things: useFrame(), which unsubscribes when its component unmounts, and flush() as the beforeRender hook.

  • Two ways to animate. 100 boxes spin. Imperative: each box's frame callback sets rotation on the three object. Signal: one callback writes a time signal, and each box reads it in its rotation prop, so Solid updates 100 props every frame. Switch and compare the update time.
  • Same-frame updates. Solid 2 applies signal writes in a microtask, after the frame callback returns, which is after the frame is drawn. Turn on the probe: it writes the frame number to a signal and reads it back from three when drawing. With flush() before render, the lag is 0 frames. Turn flush off and it becomes 1.
  • Render on demand. In demand mode the loop draws only when asked. The renderer reports every change Solid makes to the scene, so changing the color draws one frame and then the loop sleeps. Spinning boxes keep it awake. So does the probe: it writes a signal every frame, which changes the scene, which asks for another frame.
  • Unmount. Stop the spinners and their 100 callbacks unsubscribe.

JSX types

This section has no canvas: TypeScript does the checking. In Solid 2, solid-js does not own JSX types. Each renderer package provides its own jsx-runtime types, and a file picks one with jsxImportSource. These types derive each element's props from its three.js class and match what the renderer does with them.

  • One source for tags. The renderer and the types both read catalogue.js. A tag exists in the types exactly when the renderer can create it. Types over the whole three namespace accept <sphereGeometry />, which this renderer cannot create.
  • Props follow the renderer. position takes [x, y, z], because the renderer calls position.set(...value). A bare number or a Vector3 instance is a type error, because set() would get the wrong arguments. color takes a string, a number or [r, g, b]. args are checked against the constructor, events exist only on Object3D, and ref receives a node whose object has the element's class.
  • Checked both ways. One file must have no errors. In another, every line marked @ts-expect-error must be an error. If the types accept one of those lines, the check fails.
  • Cost. Six catalogue tags: about 7,400 type instantiations and 0.02 s of checking. All of three: about 14,700 and 0.13 s (TypeScript 7).
  • DOM and three in one file. The compiler can mix renderers in one file, but TypeScript reads one jsxImportSource per file. A merged namespace works for this catalogue. Across all of three, four tags clash with DOM and SVG: audio, source, line and path. A merged namespace also cannot tell which renderer owns a tag, so <div> inside <mesh> type-checks.
  • The real scenes. Checked with checkJs, the four scenes on this page have 6 JSX errors. render() from @solidjs/universal expects a single node, while a JSX expression is typed as the wider JSX.Element. And in plain JavaScript, a helper that returns [x, y, 0] is a number[], not a tuple. Props, refs, events, <Show>, <For> and <Loading> all check.
